How a bot talks to Discord

A bot is a normal program that logs in with a secret token. It talks to Discord in two ways at the same time.

REST is for actions: send a message, ban someone, register a command. Each call goes to https://discord.com/api/v10 with the header Authorization: Bot YOUR_TOKEN.

The Gateway is a WebSocket that pushes events to you: a message was sent, someone joined, a button was clicked. Your bot connects, says which events it wants (these are intents), and sends a heartbeat every few seconds so Discord knows it is alive.

Interactions are slash commands, buttons, menus and forms. You get 3 seconds to answer. If you need longer (an API call, a database query), send a "thinking…" reply first and finish later.

Webhooks are the simplest thing. A channel gets a secret URL, and anything that can send an HTTP POST can post there. No bot, no token, no connection.

Set up a bot

  1. Go to the Developer Portal and create a New Application.
  2. Open the Bot tab and reset the token. Copy it right away. Discord shows it once.
  3. Leave the privileged intents off for now. Turn on Message Content only if you need to read normal chat messages.
  4. In OAuth2, tick bot and applications.commands. Choose only the permissions you need. Open the link it makes and add the bot to a server you own for testing.
  5. Put the token in a .env file (DISCORD_TOKEN=...), and add .env to .gitignore.
  6. Run a bot from the Code page. The bot shows as online, and /ping replies.

While you build, register commands to one server (guild commands). They show up right away. Global commands can take a while.

Slash commands or prefix commands?

Use slash commands. Prefix commands like !ping need the Message Content intent, which Discord gates behind approval once your bot is in 100 servers, and they give users no help with options. Slash commands have typed options, autocomplete and permission controls built in. Prefix commands are fine for a private bot in a small server.

When it breaks

  • Bot is online but commands don't show up. You didn't register (sync) them, or you invited the bot without the applications.commands scope. Re-invite it, and register to a single server while testing.
  • "The application did not respond". You took more than 3 seconds. Defer first, then reply.
  • The bot ignores normal messages. You need the Message Content intent, turned on in the Portal and in your code.
  • Gateway closes with 4014. You asked for a privileged intent you did not enable in the Portal.
  • "Missing Permissions" (50013). The bot lacks the permission, or its role sits below the role it is trying to change. Drag the bot's role higher.
  • 401 Unauthorized. Wrong token. Reset it and copy it again, without extra spaces.

Full lists are on the error codes and close codes tables.

Webhooks

Make one in Channel settings, then Integrations. You only need the URL, so keep it secret. Anyone who has it can post to that channel.

Tip: Discord webhooks accept GitHub and Slack style payloads. Add /github or /slack to the end of the webhook URL and paste it into GitHub's webhook settings. You get commit and issue notices with no code at all.

A bot in 40 lines, with no Discord library

This shows what a library does for you: connect, read Hello, send heartbeats, Identify, read events. Install pip install websockets. It skips resuming and reconnecting, so use a real library for anything serious.

Slash commands over HTTP (no gateway)

Set an Interactions Endpoint URL in the Developer Portal. Discord sends a signed POST for each command. You must check the Ed25519 signature and answer PING, or Discord won't save your URL. This suits serverless hosting. Install pip install flask pynacl.

Register commands once

With HTTP interactions there is no gateway session to sync commands, so send them yourself.

While developing, Discord needs a public HTTPS URL. A tunnel such as ngrok or Cloudflare Tunnel points one at your laptop.

Dockerfile (Python bot)

Run it with docker run -d --restart unless-stopped --env-file .env mybot.

systemd service (any Linux server)

Save as /etc/systemd/system/mybot.service, then run sudo systemctl enable --now mybot. It restarts the bot if it crashes and starts it on boot.

Where to run it

  • Your own computer. Fine for learning. The bot goes offline when you close it.
  • A small VPS. The most predictable option. A cheap 1 GB machine handles most bots.
  • A container platform (Railway, Fly.io, Render and similar). Push your Dockerfile and set the token as a secret. Free tiers change often, so check the current terms.
  • A Raspberry Pi at home. Cheap and fun, and it needs a stable connection.

Rate limits. Each route has its own bucket, and a bot has a global cap of 50 requests per second. Responses include X-RateLimit-Remaining and X-RateLimit-Reset-After.         Learn

        Do these in order. Each step adds one idea to the bot you already have.

        1. Get online. Create the app, invite it, run the ping example.
        2. Take input. Add options to a command (numbers, users, choices). Check them.
        3. Make replies look good. Send embeds. Learn the size limits.
        4. Make it interactive. Add buttons, select menus and modals. Handle timeouts.
        5. Reach out. Call an outside API with a deferred reply and error handling.
        6. Remember things. Use SQLite first. Move to PostgreSQL when it gets big.
        7. Organize. Split code into cogs (Python) or command files (JS). Add logging.
        8. Host it. Run it 24/7 and restart it automatically after a crash.

          Rules and safety

          Learn these early. They are what get bots and accounts removed.

          About "private" APIs. Everything on this site uses Discord's documented API with a bot token. The private things that are yours to use are your bot token, client secret, OAuth2 tokens that users give you, webhook URLs, and the public key for checking interactions. Undocumented user-account endpoints, and automating a normal user account (a "self-bot"), break Discord's Terms of Service and can get the account banned. This site does not cover them.

          • Tokensnever share

            Keep them in environment variables or a secrets manager. If one leaks, even in a git commit, reset it in the Developer Portal at once.

          • Least privilegepermissions, intents

            Ask only for what you use. Avoid Administrator. Skip Message Content unless you read messages.

          • User dataprivacy

            Store only what you need, say what you store, delete it when asked. Read the Developer Policy and Terms.

          • Untrusted inputusers type anything

            Set allowed mentions so a command can't ping @everyone. Check permissions before moderation actions. Never run user text as code.

          • Failurereliability

            Catch errors in each command and reply with something useful. Log the real error for yourself. Back off on 429.

          • Paid APIscost

            Add per-user cooldowns and daily caps before you connect a paid API to a public command.
